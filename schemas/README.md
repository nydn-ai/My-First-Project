# schemas/

Avro schema definitions (`.avsc`) for all Vertex ML log event types.
These files are the source of truth for the Schema Registry and are
registered during every CI build via `scripts/register_schemas.py`.

---

## Schema Catalogue

| File | Subject (Schema Registry key) | Kafka Topic |
|------|-------------------------------|-------------|
| `vertex_prediction_log.avsc` | `com.bumble.avro.ml.vertex.VertexPredictionLog` | `dev-enriched-vertex-logs` |
| `vertex_batch_log.avsc` | `com.bumble.avro.ml.vertex.VertexBatchLog` | `dev-enriched-vertex-batch-logs` |
| `vertex_monitoring_log.avsc` | `com.bumble.avro.ml.vertex.VertexMonitoringLog` | `dev-enriched-vertex-monitoring-logs` |
| `vertex_training_log.avsc` | `com.bumble.avro.ml.vertex.VertexTrainingLog` | `dev-enriched-vertex-training-logs` |

The `online_prediction_log.avsc`, `batch_prediction_log.avsc`,
`monitoring_log.avsc`, `training_log.avsc`, and `vertex_ml_log.avsc` files
are earlier drafts / reference schemas kept for historical context.  The
`vertex_*.avsc` variants are the active ones registered in the Schema Registry.

---

## Schema Structure

All four active schemas share the same **top-level fields** (common envelope)
and differ only in their nested `payload` sub-record.

### Common Envelope Fields

| Field | Avro Type | Nullable | Description |
|-------|-----------|----------|-------------|
| `id` | `string` (uuid) | No | Unique event UUID generated by the pipeline |
| `ts` | `long` (timestamp-millis) | No | Canonical event timestamp (from Cloud Logging `timestamp`) |
| `insert_time` | `long` (timestamp-millis) | No | Wall-clock time the pipeline processed this record |
| `event_time` | `long` (timestamp-millis) | Yes | Alias of `ts`; kept for consumer compatibility |
| `log_name` | `string` | No | Cloud Logging `logName` |
| `resource_type` | `string` | No | GCP monitored resource type (e.g. `aiplatform.googleapis.com/Endpoint`) |
| `resource_labels` | `map<string>` | No | Cloud Logging `resource.labels` key-value pairs |
| `project_id` | `string` | Yes | GCP project ID extracted from `resource.labels` |
| `location` | `string` | Yes | Cloud region (from `resource.labels.location`) |
| `endpoint_id` | `string` | Yes | Vertex AI endpoint ID — used as Kafka partition key |
| `model_id` | `string` | Yes | Model ID from `protoPayload` or `jsonPayload` |
| `model_version` | `string` | Yes | Model version from `protoPayload.response` |
| `severity` | `string` | No | Cloud Logging severity label (e.g. `ERROR`, `INFO`) |
| `trace` | `string` | Yes | Distributed trace ID |
| `span_id` | `string` | Yes | Distributed span ID |
| `insert_id` | `string` | Yes | Cloud Logging `insertId` (deduplication key) |
| `payload` | record | No | Schema-specific nested payload (see below) |
| `raw_payload_json` | `string` | Yes | JSON-serialized source payload for debugging / replay |

## Payload Sub-Records

### `PredictionPayload` (`vertex_prediction_log.avsc`)

Populated from online prediction audit logs or container logs.

| Field | Type | Description |
|-------|------|-------------|
| `method` | `string?` | RPC method (`Predict`, `RawPredict`, etc.) |
| `deployed_model_id` | `string?` | ID of the deployed model that served the request |
| `latency_ms` | `long?` | End-to-end prediction latency in milliseconds |
| `status_code` | `int?` | HTTP or gRPC status code |
| `request_size_bytes` | `long?` | Serialized request size |
| `response_size_bytes` | `long?` | Serialized response size |
| `request_payload_json` | `string?` | Serialized request body (may contain user data) |
| `response_payload_json` | `string?` | Serialized response body |
| `error_message` | `string?` | Human-readable error when prediction fails |

### `BatchPayload` (`vertex_batch_log.avsc`)

Populated from batch prediction job lifecycle audit logs.

| Field | Type | Description |
|-------|------|-------------|
| `batch_job_id` | `string?` | Batch prediction job ID |
| `batch_job_name` | `string?` | Human-readable job display name |
| `job_state` | `string?` | Job lifecycle state (e.g. `JOB_STATE_RUNNING`) |
| `input_uri` | `string?` | GCS source URI for batch inputs |
| `input_format` | `string?` | Input instances format (e.g. `jsonl`) |
| `output_uri` | `string?` | GCS destination URI prefix |
| `output_format` | `string?` | Output predictions format |
| `instance_count` | `long?` | Number of instances processed |
| `success_count` | `long?` | Successfully predicted instances |
| `failure_count` | `long?` | Failed instances (from `partialFailures`) |
| `create_time` | `long?` | Job creation timestamp (epoch ms) |
| `start_time` | `long?` | Job start timestamp (epoch ms) |
| `end_time` | `long?` | Job end timestamp (epoch ms) |
| `error_code` | `string?` | RPC error code |
| `error_message` | `string?` | Error description |

### `MonitoringPayload` (`vertex_monitoring_log.avsc`)

Populated from model monitoring lifecycle audit logs and Cloud Monitoring
violation alert events.

| Field | Type | Description |
|-------|------|-------------|
| `monitoring_job_id` | `string?` | Monitoring job ID or Cloud Monitoring policy ID |
| `monitoring_job_name` | `string?` | Job or policy display name |
| `monitor_type` | `string?` | Monitor type (e.g. `ViolationOpenEventv1`, `drift`) |
| `objective_type` | `string?` | Monitoring objective |
| `feature_name` | `string?` | Feature name associated with the alert |
| `metric_name` | `string?` | Metric being monitored (heuristic from policy name) |
| `metric_value` | `double?` | Observed metric value |
| `threshold_value` | `double?` | Alert threshold |
| `alert_triggered` | `boolean?` | Whether the alert fired |
| `baseline_dataset_uri` | `string?` | Training baseline dataset GCS URI |
| `target_dataset_uri` | `string?` | Target (production) dataset GCS URI |
| `prediction_log_source` | `string?` | Source of prediction logs for monitoring |
| `window_start` | `long?` | Monitoring window start (epoch ms) |
| `window_end` | `long?` | Monitoring window end (epoch ms) |

### `TrainingPayload` (`vertex_training_log.avsc`)

Populated from CustomJob, TrainingPipeline, and HyperparameterTuningJob audit
logs, plus supplementary metric events from `jsonPayload`.

| Field | Type | Description |
|-------|------|-------------|
| `training_job_id` | `string?` | Training job ID |
| `training_job_name` | `string?` | Job display name |
| `job_state` | `string?` | Job lifecycle state |
| `worker_pool_id` | `string?` | Worker pool identifier |
| `replica_type` | `string?` | Replica type (e.g. `MASTER`) |
| `machine_type` | `string?` | GCE machine type |
| `accelerator_type` | `string?` | GPU/TPU accelerator type |
| `accelerator_count` | `int?` | Number of accelerators |
| `container_uri` | `string?` | Training container image URI |
| `args` | `array<string>?` | Container launch arguments |
| `hyperparameters` | `map<string>?` | Hyperparameter key-value pairs |
| `metrics` | `array<TrainingMetric>?` | Training metrics (name, value) |
| `artifact_uris` | `array<string>?` | Model artifact GCS URIs |
| `error_code` | `string?` | RPC error code |
| `error_message` | `string?` | Error description |

## Schema Conventions

- **Namespace:** `com.bumble.avro.ml.vertex`
- **Compatibility mode:** `BACKWARD` — new schema versions must be readable by
  consumers running the previous version.  This means:
  - You may **add** new nullable fields (with `"default": null`).
  - You may **never** remove or rename existing fields.
  - You may **never** change a field's type to an incompatible type.
- **Extension metadata:** `x-meta` top-level keys (`x-meta.ops_impact`,
  `x-meta.owners`, etc.) are stripped before registration because some
  registry implementations reject unknown top-level keys.
- **All optional fields** in the `payload` sub-records use `["null", TYPE]`
  union with `"default": null`.

## Registering Schemas

```bash
# Register / update all schemas (idempotent — safe to re-run)
python scripts/register_schemas.py \
  --registry_url https://managedkafka.googleapis.com/v1/projects/PROJECT/locations/REGION/schemaRegistries/REGISTRY

# Dry-run — see what would be registered without making changes
python scripts/register_schemas.py --registry_url ... --dry-run

# Verify all subjects exist (useful in CI after a PR schema deploy)
python scripts/register_schemas.py --registry_url ... --check

# Register only missing schemas (safe for mixed environments)
python scripts/register_schemas.py --registry_url ... --missing-only
```

## Adding a New Schema

1. Create the `.avsc` file in this directory following the namespace convention.
2. Add an `x-meta` block with `ops_impact`, `data_value`, `jira`, `owners`,
   and `life_cycle.renew_by` to comply with governance requirements.
3. Add the new `(subject, filename, references)` tuple to `SCHEMA_PLAN` in
   `scripts/register_schemas.py`.
4. Add a new mapper class in `pipeline/utils/log_type_mappers.py`.
5. Add the new `log_type` to `LOG_TYPES` in `pipeline/main.py` and the
   `log_type` variable validation in `terraform/dev/variables.tf`.
6. Add tests in `tests/`.
